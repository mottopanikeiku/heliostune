Triton matmul tuning across four GPUs

A Triton autotuner measured against torch.matmul on T4, A10, L4 and H100. In the original four-GPU comparison, the configuration picked on one timing pass was within 0.7% of the fastest of the 36 on a second pass, yet Triton on the H100 still trailed torch. Ten new kernels cut its H100 latency by 27%.

Four GPUs, the same 96 workloads

The suite covers attention and FFN projections from Granite, Mistral, Phi and Qwen at M = 1, 7, 31, 96, 257 and 1024. There are 84 distinct shapes. Ratios are geometric means; lower is faster. Selection overhead compares the fixed pass-1 choice with the fastest configuration measured on pass 2.

Selection and scoring

Pass 1 times all 36 original configurations, 6 new ordinary and persistent actions, and 4 split-K actions when M ≤ 31 (4,224 candidate measurements). For each workload, it selects the lowest valid median separately from the old set, the new set and their union, breaking ties by configuration key. Pass 2 times only those fixed choices (192 candidate measurements). Both passes time torch once per workload. The JSON files call these passes banks 1 and 2. See the measurement method.

The combined set's pass-1 choice also wins the old-versus-new comparison on pass 2 for 96/96 workloads. This page measures exhaustive selection; Thompson sampling has not been rerun on the expanded set.

Selection loss across the stored measurements

For each pair of timing passes, I select the fastest valid action on the earlier pass and score it on the later pass. The comparison is the later pass's own minimum. Across 19 multi-pass archives, the selection is at most 0.83% slower in geometric-mean latency. The same-pass minimum ranges from 0.936× to 3.828× torch. Where the gap is large, the kernel set is the main constraint.

Kernel layout

Inference: these program counts, padding fractions and workspace sizes come from the source configurations, not profiler measurements.

Implementations

  • old / tile (src/heliostune/kernel.py): Grouped tl.load/tl.dot matmul. The four new tile actions use larger launch parameters.
  • persistent (src/heliostune/hopper_kernel.py): Adapted from Triton 3.4.0's persistent-matmul tutorial; warp specialization and epilogue subtiling are disabled.
  • split_k (src/heliostune/action_expansion.py): Tensor-core partial tiles, an FP32 workspace and a separate reduction with one FP16 conversion.

Formulas

ideal bytes
2*(M*K+K*N+M*N) FP16 bytes, one read per operand and one output write
intensity
useful GEMM FLOPs 2*M*N*K divided by logical bytes; split-K adds workspace traffic to the denominator
launches
ordinary/persistent: 1; tensor-core split-K: 2 (partials and reduction)
masked rows
1-M/(Tm*BM); masked dot lanes, NOT a fraction of latency or HBM bytes
no cross tile reuse
2*(Tn*M*K+Tm*K*N+M*N) + workspace write/read; no inter-tile input reuse
padded dot
2*(Tm*BM)*(Tn*BN)*(S*Tk*BK); source-level padded dot work, not instruction counts
persistent balance
each persistent program strides tiles by SMs: at most ceil(Tm*Tn/P) tiles per program; balance = Tm*Tn/(P*ceil(Tm*Tn/P)), 1 when every program gets the same tile count
programs
ordinary: Tm*Tn; persistent: min(SMs,Tm*Tn); split-K: S*Tm*Tn plus ceil(M*N/256) reduction programs
tiles
Tm=ceil(M/BM), Tn=ceil(N/BN), Tk=ceil(ceil(K/BK)/S); S=1 except split-K
workspace
4*S*M*N FP32 bytes; write plus read = 8*S*M*N; unpadded; zero without split-K
